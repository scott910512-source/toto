# 또또 아기수첩 · 코드 구조

> 저장소 루트의 `README.md` 와 `index.html` 은 **다른 프로젝트(주말 뭐하지?)** 것입니다.
> 이 저장소는 브랜치마다 다른 프로젝트가 들어 있고, 또또는
> `claude/baby-care-firebase-app-QPyK0` 브랜치입니다.

## 지금 어떤 파일이 돌아가고 있나

| 주소 | 파일 | 상태 |
|---|---|---|
| `/toto/app.html` | `app.html` | **가족이 쓰는 화면** |
| `/toto/dday.html` | `dday.html` | 전체화면 D-day (아이패드 거치용) |
| `/toto/` | `index.html` | 다른 프로젝트 것 (또또 아님) |
| 배포 안 됨 | `web/index.html` + `src/` | 새 구조로 옮기는 중 |

GitHub Pages 설정이 **Deploy from a branch** 라서, 이 브랜치에 푸시하면
검사를 통과하지 않아도 바로 배포됩니다. 검사를 통과한 것만 올리려면
`Settings → Pages → Source` 를 **GitHub Actions** 로 바꾸면 `deploy.yml` 의
게이트가 걸립니다.

## 왜 파일이 두 갈래인가

`app.html` 은 6천 줄 단일 파일입니다. 브라우저에서 Babel 로 바로 컴파일되므로
`import` 를 쓸 수 없고, 한 번에 새로 쓰면 가족이 쓰는 앱이 멈춥니다.
그래서 **로직부터 한 벌로 합치고, 화면은 뒤에 옮기는** 순서로 갑니다.

```
src/ (TypeScript · 테스트 있음)
 ├─ lib/            날짜 · 오류문구 · 설정진단 · 백업 · 쓰기지시 · 사진주소
 │                  공개범위 판단 · 메달 · 참고안내
 ├─ repositories/   DB 행↔객체 변환 · Firestore 문법 → Supabase 계층
 ├─ hooks/          주소 기억 · 어두운 화면 · 흐르는 시간 · 모달 초점
 ├─ components/ui/  Card · Btn · Spinner · Field · ChipGroup · Portal · Modal
 ├─ providers/      알림(실행취소) · 로그인/권한
 ├─ screens/        옮겨 온 화면 (메달 판)
 └─ legacy-bridge.ts  ↑ 로직을 묶어 vendor/toto-core.js 로 빌드
          │
          ▼
app.html  window.TotoCore 에서 꺼내 쓴다 (사본 없음)
```

`vendor/` 의 파일들은 **빌드 결과물인데 저장소에 커밋**합니다. Pages 가
브랜치를 그대로 내보내 배포 시 빌드 단계가 없기 때문입니다. 소스만 고치고
빌드를 잊으면 가족은 예전 코드를 쓰게 되므로, `npm run verify` 가 **다시
빌드해 비교**합니다.

| 파일 | 원본 | 만드는 명령 |
|---|---|---|
| `vendor/toto-core.js` | `src/legacy-bridge.ts` | `npm run build:core` |
| `vendor/app-compiled.js` | `app.html` 안의 `#toto-source` | `npm run build:app` |
| `vendor/app.css` | `app.html` 에 쓰인 Tailwind 클래스 | `npm run build:css` |
| `vendor/toto-sql.js` · `migrations/mobile/*` | `migrations/004·005` | `npm run build:sql` |

### 앱을 미리 컴파일하는 이유

예전에는 브라우저가 앱을 열 때마다 **@babel/standalone 2.9MB 를 내려받고
5,700줄 JSX 를 컴파일**했습니다. 폰에서는 이게 시작 시간의 대부분이었습니다.

지금은 `vendor/app-compiled.js` 가 이미 컴파일된 결과이고, Babel 은
**그 파일을 못 받았을 때만** 내려받습니다.

- `app.html` 안의 `#toto-source` 가 **여전히 원본**입니다. 고칠 때는 여기를
  고치고 `npm run build:app` 을 돌립니다 (`verify` 가 빠뜨림을 잡습니다).
- 측정값 (2026-10-03, 이 기계 · Babel 도 로컬):
  미리 컴파일 **638ms** vs Babel 직접 **1829ms** → **1.2초** 빨라짐.
  폰에서는 2.9MB 내려받기까지 빠지므로 차이가 더 큽니다.
- 되돌림 경로도 테스트합니다 (`e2e/precompiled.spec.ts`). 테스트하지 않은
  되돌림은 되돌림이 아닙니다.
- 다시 재 보려면: `npx playwright test -c tools/bench/playwright.config.ts --project=desktop startup`

### Tailwind 도 미리 만든다

예전에는 `cdn.tailwindcss.com` 398kB 를 받아 브라우저가 페이지의 클래스를 훑어
그 자리에서 CSS 를 만들었습니다(JIT). 지금은 `vendor/app.css`(28kB)가 그 결과입니다.

- 측정 (2026-10-05, 이 기계 · CDN 도 로컬): 스타일 입혀지기까지
  **207ms** vs **479ms** → **272ms** 빨라짐. 폰에서는 398kB 내려받기도 빠집니다.
- `app.html` 에 클래스를 새로 쓰면 `npm run build:css` 를 돌립니다. 잊으면
  `verify` 가 막습니다 — 안 돌리면 그 버튼만 스타일이 빠진 채 배포됩니다.
- 동적으로 조립되는 클래스(`bg-${color}-500` 같은 것)는 쓰지 마세요. 빌드가
  못 보고 빠집니다. 지금 코드에는 하나도 없습니다.
- 못 받으면 `<link onerror>` 가 CDN 으로 되돌립니다. 되돌림 함수는 반드시
  링크보다 앞에 둡니다 — 뒤에 두면 onerror 보다 먼저 돌아 영영 안 켜집니다.
- 재 보려면: `npx playwright test -c tools/bench/playwright.config.ts --project=desktop css`

### 차트 라이브러리는 필요할 때만 받는다

Recharts(487kB)는 첫 로딩 외부 파일 중 가장 큰데, 출산 전 홈은 차트를
하나도 안 그리고 출산 뒤에도 기록 탭 몇 개와 통계 모달에서만 씁니다.
그래서 **차트가 처음 그려질 때** 앱이 받습니다(`loadRecharts`).

- Recharts 는 자식의 타입으로 축·막대·선을 알아봅니다. 그래서 `<XAxis>` 같은
  자식 자리는 표시만 하는 빈 컴포넌트로 두고, 차트 프록시(`BarChart`·
  `LineChart`)가 그릴 때 그 표시를 진짜 타입으로 바꿔 넘깁니다.
  호출부는 한 줄도 안 바뀝니다.
- 이 방식은 "차트 > 직접 자식" 모양에서만 됩니다. 차트 요소를 변수에 담거나
  props 로 넘기지 마세요 (지금 코드 7곳은 전부 직접 자식입니다).
- 못 받으면 그 자리에 "차트를 불러오지 못했어요" 만 뜨고 나머지는 멀쩡합니다.
- `e2e/charts.spec.ts` 가 출산 전 홈에서 안 받는지, 받았을 때 SVG 안에
  막대·축·범례가 실제로 만들어지는지(글자만이 아니라) 확인합니다.
- E2E 픽스처는 `vendor/app-compiled.js` 안의 CDN 주소도 로컬 사본으로
  바꿉니다. 지연 로딩 주소가 그 안에 있기 때문입니다.

### 조회가 실패하면 "없어요" 가 아니라 "불러오지 못했어요"

구독 훅(`useRecords`·`usePhotos`·가족 정보)은 성공/실패를 `dbHealth`
(`src/lib/dbHealth.ts`)에 알리고, 머리글 아래 배너 하나가 그 상태를 보여줍니다.

- 연결 실패 → "다시 시도" (tick 이 올라가 훅들이 다시 구독)
- 로그인 만료(`JWT expired`·`PGRST301`) → "로그아웃"
- 오프라인 → 안내만, `online` 이벤트가 오면 스스로 다시 조회
- 실패해도 목록은 빈 배열로 둡니다. 스피너가 영영 돌지도, 가족이 "기록이
  사라졌나" 하고 놀라지도 않게.
- `e2e/health.spec.ts` 가 확인합니다. 스텁은 `dbError` 시드와
  `window.__E2E.dbError` 로 실패를 흉내냅니다.

### 홈은 시기별로 제 것만 구독한다

`Dashboard` 는 시기만 고르고 `PregnantHome`(초음파 1개) / `BornHome`(수유·수면·
기저귀 등 6개)이 각자 구독합니다. 아기 정보가 DB 에서 오기 전에는 스피너를
둡니다 — 기본값이 임신 중이라 태어난 아기네도 잠깐 출산 전 홈이 떴었습니다.
`e2e/home-queries.spec.ts` 가 `window.__E2E.reads` 로 조회 목록을 셉니다.

### Realtime 채널은 테이블당 하나

`legacyStore` 의 구독은 같은 테이블이면 채널 하나를 나눠 쓰고(`listenTable`),
마지막 구독이 끝날 때 닫습니다. 예전에는 구독마다 채널을 열어 홈만 열어도
`records` 채널이 7개였고, 기록 하나가 바뀌면 서버가 7번 알렸습니다
(Realtime 메시지 한도를 그만큼 빨리 씁니다).

알림에는 바뀐 행이 실려 옵니다. `where` 조건이 있는 구독은 그 조건에 안 맞는
INSERT·UPDATE 는 무시합니다 — 수유 구독이 편지가 추가됐다고 다시 읽지 않습니다.
DELETE 는 id 만 오므로 거르지 않고 읽습니다 (모르면 읽는 쪽이 안전합니다).

## 명령어

```bash
npm run verify      # 운영 파일 문법 + 되돌아오면 안 되는 것 + 빌드 결과물 일치
npm test            # 단위 테스트 (src/)
npm run test:sql    # 임시 PostgreSQL 에 마이그레이션 올려 RLS 권한 검사
npm run e2e         # 실제 app.html 을 띄워 아이폰·아이패드·데스크톱에서 검사
npm run lint        # ESLint
npm run build       # 새 구조(web/) 빌드 — 아직 배포 대상 아님
npm run build:core  # vendor/toto-core.js 다시 만들기
npm run build:app   # vendor/app-compiled.js 다시 만들기 (app.html 고친 뒤)
npm run build:css   # vendor/app.css 다시 만들기 (app.html 에 클래스 추가한 뒤)
npm run build:sql   # 모바일용 짧은 SQL · 조각 다시 만들기
npm run dev         # 새 구조 개발 서버 (작업대 화면)
```

`npm run dev` 로 열리는 화면은 **작업대(Workbench)** 입니다. 옮겨 온 조각이
실제로 동작하는지 눈으로 보는 자리이고, 가족이 쓰는 화면이 아닙니다.

### 접속 정보

새 구조는 두 곳에서 읽습니다 (`src/lib/readConfig.ts`).

1. 빌드할 때 넣은 `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`
2. 없으면 `supabase-config.js` 가 `window` 에 올려둔 값 — **app.html 과 같은 파일**

2번이 있어서 접속 정보가 두 곳으로 갈리지 않고, 저장소에 키를 넣을 일도
없습니다. `service_role` 키를 넣으면 `diagnoseConfig` 가 앱을 띄우지 않고
무슨 키인지 경고합니다.

### 화면을 옮기는 순서

1. 화면이 쓰는 로직이 `src/` 에 있는지 확인 (없으면 먼저 옮기고 테스트)
2. 화면을 `src/screens/` 에 TSX 로 옮기고 **단위 테스트**를 붙인다
3. 옮기면서 찾은 문제는 **`app.html` 에도 같이 반영**한다 — 가족이 쓰는 건
   아직 그쪽이다
4. 작업대에 끼워 눈으로 확인한다
5. `app.html` 과 동등해지면 그때 진입점을 바꾼다 (아직 하지 않음)

## 되돌아오면 안 되는 것

`tools/verify-legacy.mjs` 가 매번 막습니다. 고치려다 되돌린 적이 있는 것들입니다.

- 비밀번호를 `localStorage` 에 저장
- `service_role`(비밀) 키가 코드에 들어감
- 프론트에서 `role` / `approved` / `disabled` 를 직접 씀
- 이메일만으로 관리자 권한을 줌
- `src/` 에 있는 로직의 사본이 `app.html` 에 다시 생김
- 12px 보다 작은 글씨, `🚨`, `비정상` 같은 판정 문구
- `APP_VERSION` 과 서비스워커 `CACHE` 버전이 어긋남
- 44px 보다 작은 터치 영역 (`tools/check-touch-size.mjs`)
- 스크린리더용 화면 제목(`h1.sr-only`)이 사라짐
- `vendor/` 의 빌드 결과물이 원본과 어긋남
- 서비스워커 오프라인 목록에 없는 파일이 적혀 있음

## DB

`supabase/README.md` 를 보세요. 실행 순서와 각 파일이 무엇을 하는지 적어뒀습니다.
아이패드에서 붙여넣기 어려우면 앱의 **더보기 → 🛠 DB 보안 수정** 에서
조각별로 복사할 수 있고, 그 카드는 적용됐는지 DB 에 직접 물어봅니다.

## 배포할 때

1. `npm run verify && npm test && npm run test:sql && npm run e2e` 전부 통과
2. `app.html` 의 `APP_VERSION` 과 `sw.js` 의 `CACHE` 를 같이 올림
   (안 올리면 "최신으로 새로고침" 을 눌러도 폰이 예전 화면을 보여줍니다)
3. `app.html` 을 고쳤으면 `npm run build:app` 과 `npm run build:css`, `src/` 를 고쳤으면
   `npm run build:core` (잊으면 `verify` 가 막습니다)
4. 브랜치에 푸시 → Pages 가 자동 배포
5. 폰에서 앱을 열면 "새 버전이 있습니다" 배너가 뜹니다
